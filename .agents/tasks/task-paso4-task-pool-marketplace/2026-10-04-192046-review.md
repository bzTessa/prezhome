# Task Pool "Bolsa Común" and Rewards Marketplace for PrezHome (v1)

Paso 4 adds a common pool of unassigned chores and a points-based rewards marketplace on top of the existing task/economy screens. The model gains an informational `effort_points` field (backward-compatible), the scheduler grows a `claimAndComplete` flow that assigns an unclaimed task to the caller and then runs the unchanged award+reschedule logic, and a migration adds `rewards` / `reward_redemptions` tables with per-home RLS plus a `SECURITY DEFINER redeem_reward` RPC that validates the caller's balance server-side. The tasks screen surfaces the pool with a "Yo me encargo" button; the economy screen is reframed around a points balance between members and a redeemable catalog, with the pre-existing tickets/budget/stats UI preserved under a "Gastos y tickets" sub-section.

Watch for: claiming a **recurrent** pool task assigns it permanently to the claimer so it leaves the pool forever after one completion (confirmed); the pool renders in a non-scrollable region stacked above the task list and can overflow with enough unclaimed tasks (likely); unassigned tasks appear in two places at once with two different complete flows (confirmed); the redeem RPC does not lock rows, so two concurrent redeems can both pass the balance check (possible).

**Verdict**: NEEDS_CHANGES

## High-level view

The server-side trust boundary is sound. `redeem_reward` is `SECURITY DEFINER` with a fixed `search_path`, computes the balance from `task_points` minus `reward_redemptions` on the server, and refuses when it is short — the client-side balance only grays out a button and cannot be used to overspend. RLS on both new tables is keyed on `public.auth_home_id()`, redemptions require `redeemed_by = auth.uid()` on insert, and the ledger is append-only (no update/delete policy or grant). The migration is idempotent and well-formed.

The pool semantics have a sharp edge on recurrent tasks. "Yo me encargo" sets `assigned_to` before awarding points, which is correct for a one-off chore, but a recurrent task is rescheduled (`is_done=false`) and keeps the assignee — so it reappears owned by whoever claimed it first and never returns to the common pool. Whether that is the intended product behavior is a decision the author should confirm; the code silently makes recurrent pool tasks single-owner after one claim.

The pool UI is a fixed-height block sitting between the points chart and the `Expanded` task list, not inside a scroll view, so a household with several unclaimed tasks can push the column past the viewport. The same unassigned tasks also render a second time in the main list below, where the normal complete button runs a different flow (no assignment).

The redeem RPC validates balance but reads `task_points` and `reward_redemptions` without any lock, so two redemptions fired close together can each see the full balance and both succeed, driving the stored balance negative even though the UI clamps the display at zero.

1. **Recurrent task leaves the pool permanently** — `claimAndComplete` sets `assigned_to` on a recurrent task and then reschedules it, so it reappears privately owned and never returns to the Bolsa Común. 4. **Concurrent redeem double-spend** — `redeem_reward` reads balance without row locking, so two near-simultaneous redeems can both pass and overdraw the balance. Serialize via `select ... for update` on a per-user anchor or a balance check inside a locked statement.
5. **effort_points unused** — the new column and chip are purely informational and never affect scoring; confirmed as intended per the comments, flagged only so reviewers know it is inert.

### Claim-then-complete and the recurrent-task edge

`claimAndComplete` writes `assigned_to = user.id` on the task row, then delegates to the shared `_awardAndReschedule` helper that `complete()` also uses. The refactor keeps `complete()`'s observable behavior byte-for-byte (same `task_points` insert, same `completeOnceMap`/`rescheduleMap` calls, now parameterized by `userId`), so the Inicio dashboard is unaffected, and the claim path awards points exactly once per invocation.

The edge is recurrence. A recurrent pool task runs through `rescheduleMap`, which sets `is_done=false` and advances `due_date`/`next_due` — but the `assigned_to` write from the claim persists. The task therefore reappears on its next occurrence permanently owned by the first claimer and `isInPool` is false forever after, so it never returns to the common pool for someone else to pick up. If the product intent is "the pool is a backlog of one-off chores," this is acceptable; if the intent is "anyone can grab the next occurrence each time," the assignment should be scoped to `once` tasks or cleared during reschedule for tasks claimed from the pool.

### Pool rendering stacked above the task list

```
Column
 ├─ _Scoreboard            (fixed)
 ├─ _PointsChart           (fixed)
 ├─ _TareasCelebracion     (fixed)
 ├─ _BolsaComun            (fixed, non-scrollable Column of pool cards)
 └─ Expanded(task list)    (scrollable)
```

`_BolsaComun` lays its pool cards out in a plain `Column` with no scroll affordance, and it sits inside the outer `Column` alongside the scoreboard and chart, competing for the viewport's fixed vertical budget before the `Expanded` list claims the rest. On a short screen with a handful of unclaimed tasks this overflows the fixed region (RenderFlex overflow). Folding the pool into the scrollable list region, or giving it a bounded, independently scrollable height, avoids this.

### Duplicate presentation of unassigned tasks

`_load` computes `pool = tasks.where((t) => t.isInPool && !t.isDone)` but the main list below renders `data.tasks` unfiltered. An unassigned, not-done task therefore shows up twice: once in "Bolsa Común" with a "Yo me encargo" button wired to `claimAndComplete` (assign + award), and once in the main list with its normal complete button wired to `_complete` → `complete()` (award, no assignment). Beyond the visual duplication, the two entry points produce different row states for the same task, which is easy to trip over during QA. Filtering pool tasks out of the main list (or vice versa) resolves both the duplication and the divergent-flow ambiguity.

### Server-side balance enforcement in redeem_reward

The RPC inserts the ledger row with `cost_points` copied from the reward row (not from client input), under `SECURITY DEFINER` with `set search_path = public, pg_temp`, after computing `coalesce(sum(task_points.points)) - coalesce(sum(reward_redemptions.cost_points))` server-side and raising `Saldo insuficiente` when short. The client-side `canRedeem = myBalance >= cost` gate in `_rewardRow` only sets button opacity/enablement; it is not the authority, so a tampered client cannot overspend in a single call.

The gap is concurrency. The balance is read with two unlocked aggregate subqueries, so two redemptions issued close together each observe the pre-spend balance, both pass the `v_balance < v_cost` check, and both insert — overdrawing the real balance. The display clamps at zero via `PointsBalance.forUser`, which hides the overdraft rather than preventing it. A `select ... for update` on a per-user row (or an advisory lock keyed on the user) around the balance computation closes this.

### RLS and cross-home isolation

Both new tables gate select/insert on `home_id = public.auth_home_id()`. `reward_redemptions` has only select+insert policies and grants (no update/delete), keeping the ledger append-only, and its insert policy pins `redeemed_by = auth.uid()` so a user cannot write a redemption in someone else's name. `rewards` allows update/delete within the home, which is the intended "both members manage the catalog" posture. No cross-home read path was found: the economy screen queries `task_points`/`reward_redemptions`/`rewards` filtered by `home_id` with RLS backing it.

### Preserved tickets/budget/stats

The month navigator, budget card/`_editBudget`, spend trend chart, historical card, ticket list/`_deleteTicket`, `_openScan` and `ProductStatsScreen` access all survive under a "GASTOS Y TICKETS" sub-section; the only edit there replaces an inline `Colors.grey[500]` header with the shared `_sectionLabel`. The second FAB's `heroTag: 'fab-reward'` is distinct from `fab-economy`, so no Hero collision.

### Design-system and motion conformance

No "IA"/"AI" strings were added and new code stays on theme tokens; the only `Colors.*` additions are `Colors.red`/`Colors.redAccent` on error SnackBar backgrounds, matching the existing convention across screens (not new raw literals). `AnimatedCounter` and `Celebrate.show` honor reduce-motion internally.

### Test coverage

`task_pool_test.dart` meaningfully exercises the new pure logic: the `effort_points` fallback chain (explicit value, fall back to `points`, fall back to `10`), `toInsertMap` serialization, `isInPool` true/false, and `PointsBalance.forUser` arithmetic including the negative-clamp case. The sentinel `_absent` object correctly distinguishes a missing column from a null value, so the fallback tests are honest and would fail if the fallback were removed.

Not tested: `claimAndComplete`'s assignment write and its interaction with recurrent reschedule (the recurrent-ownership edge above is entirely uncovered), the redeem RPC behavior (understandable — no live DB in the sandbox), and the duplicate-rendering / overflow UI concerns. The pure-logic coverage is solid; the behavioral risks flagged here sit in the untested service/UI seams.
