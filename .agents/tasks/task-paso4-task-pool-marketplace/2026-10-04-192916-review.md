# Task Pool "Bolsa Común" and Rewards Marketplace — follow-up (v2)

Second-pass review after the author addressed the five v1 findings. The recurrent-claim ownership edge is now handled by a `releaseToPool` flag threaded from `claimAndComplete` through `rescheduleMap`; the tasks screen was refactored into a single scrolling `ListView` and now filters pool tasks out of the main list; and migration 0042 gained a per-user advisory lock in `redeem_reward`. Each fix was checked against the code, not just the author's claim, and the three previously-untested behaviors (default reschedule, release-to-pool, once-stays-attributed) are now covered by pure tests.

Watch for: nothing blocking. One benign cosmetic nuance remains — when the only pending work lives in the pool, the main list renders its "no tasks" empty state directly below a populated Bolsa Común (possible). Not a regression and not worth gating on.

**Verdict**: APPROVED

## High-level view

Issue 1 (recurrent task leaves the pool forever) is genuinely fixed and the fix is surgical. `HomeTask.rescheduleMap` now takes `releaseToPool` defaulting to `false`, and only emits `assigned_to: null` when it is true. `complete()` never sets it, so its write set is byte-for-byte what it was and the Inicio dashboard and normal recurrence are untouched. `claimAndComplete` passes `releaseToPool: true`, so a recurrent task claimed from the pool returns to the Bolsa Común on its next occurrence, while a `once` task takes the early `completeOnceMap` return (which never writes `assigned_to`) and stays attributed to whoever did it. The asymmetry is correct in both directions.

Issue 2 (pool overflow) is fixed by replacing the `Column` + `Expanded` body with a single `ListView`: scoreboard, chart, celebration, and Bolsa Común are now scrollable leading items and the task cards follow, so no fixed-height region can RenderFlex-overflow. The scoreboard, chart, celebration, and both FABs survived the refactor.

Issue 3 (unassigned tasks rendered twice) is fixed by computing `listTasks = tasks.where((t) => !(t.isInPool && !t.isDone))` and rendering that in the main list, so an unassigned pending task appears only in the pool, while assigned and done tasks still render in the main list with the unchanged `_complete` flow. Single source of truth per row.

Issue 4 (concurrent redeem double-spend) is fixed by `pg_advisory_xact_lock(hashtextextended(v_user_id::text, 0))` taken after the reward lookup and before the balance read. The transaction-scoped lock serializes concurrent redeems by the same user (auto-released at RPC end) while keying on the user so other users never block. The function stays `SECURITY DEFINER` with a fixed `search_path`, still computes the balance server-side from `task_points` minus `reward_redemptions`, copies `cost_points` from the reward row (not client input), and remains idempotent.

Issue 5 (effort_points inert) is unchanged and documented as an informational "Esfuerzo: N" chip; scoring deliberately uses `HomeTask.points`. Accepted as a trade-off, not a defect.

### Recurrent-claim ownership (Issue 1)

The one place the flag changes behavior is the recurrent-reschedule branch of `rescheduleMap`:

```dart
if (releaseToPool) 'assigned_to': null,
```

A `once` task returns early through `completeOnceMap`, which has no `assigned_to` key regardless of the flag — so a claimed one-off stays attributed, matching the user instruction ("asigne la tarea, la complete y sume los puntos"). The three new tests pin all three cases: default omits the key, `releaseToPool: true` sets it to null, and `completeOnceMap` never reassigns.

### Single scroll (Issue 2)

`todoHecho` is computed from `data.tasks` (all tasks), not `listTasks`, so the celebration correctly stays false while unclaimed pool work remains and does not fire prematurely.

### Deduplicated rendering (Issue 3)

`pool` and `listTasks` are exact complements over the `isInPool && !isDone` predicate, so each row renders in exactly one place with exactly one complete flow (`claimAndComplete` in the pool, the unchanged `complete()` in the main list). The one cosmetic artifact: `listTasks.isEmpty` drives the main-list `_empty()` even when the pool is non-empty, so a pool-only state shows an empty-list message under a populated pool.

### Advisory lock in redeem_reward (Issue 4)

```sql
perform pg_advisory_xact_lock(hashtextextended(v_user_id::text, 0));
v_balance := coalesce((select sum(tp.points) ...), 0)
           - coalesce((select sum(rr.cost_points) ...), 0);
if v_balance < v_cost then raise exception 'Saldo insuficiente ...'; end if;
insert into public.reward_redemptions (...) values (...);
```

The lock is acquired before the balance is read, so a second concurrent redeem for the same user blocks until the first commits its insert, then recomputes the balance including that spend — closing the double-spend window from v1. The key is a stable hash of the user id, so distinct users take distinct locks and never contend. Everything else that made the trust boundary sound in v1 is intact and was re-verified: `security definer` with `set search_path = public, pg_temp`, server-side balance, `cost_points` sourced from the reward row (not client input), append-only ledger (no update/delete policy or grant), and insert policy pinning `redeemed_by = auth.uid()`. Migration remains idempotent.

### Regression sweep

No new user-facing "IA"/"AI" strings in the touched screens (the only matches are in task-metadata JSON and prior review prose, not code). No new raw color literals: new code uses `AppColors.*` and `AppTheme.cardDecoration`; the only literal `Colors.*` are `Colors.red`/`Colors.redAccent` on error SnackBar backgrounds, matching the existing convention. FAB hero tags remain distinct (`fab-reward` vs `fab-economy`). The economy screen still exposes `_editBudget`, `_deleteTicket`, `_openScan`, and `ProductStatsScreen` under the preserved "GASTOS Y TICKETS" section — tickets, budget, and stats are intact. The redeem call passes only `p_reward_id`; cost is never trusted from the client.

### Test coverage

The v1 gap — `claimAndComplete`'s recurrent interaction being entirely untested — is now addressed at the pure-logic layer: `rescheduleMap` default-omits `assigned_to`, includes `assigned_to: null` under `releaseToPool`, and `completeOnceMap` never reassigns. Combined with the retained `effortPoints`/`isInPool`/`PointsBalance` tests, the pure surface is well covered (215 passing, up from 212). Still untested, acceptably: the Supabase-side writes in `claimAndComplete`/`_awardAndReschedule` and the `redeem_reward` RPC (no live DB in the sandbox), and the UI dedup/scroll behavior (widget-test territory). The behavioral risk that mattered — recurrent ownership — is now pinned by the reschedule-map tests.
