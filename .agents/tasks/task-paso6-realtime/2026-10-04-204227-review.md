# Supabase Realtime for shopping list and tasks — fix pass (v2)

Follow-up on the v1 review (NEEDS_CHANGES, 4 issues). Commit `9ef75b4` applies fixes on top of the original feature `9573bad`: migration 0043 now sets `REPLICA IDENTITY FULL` on both tables so filtered DELETEs survive, both channel topics are made instance-unique via `identityHashCode(this)`, shopping's `_subscribeRealtime` resolves `home_id` inline and returns silently on a missing session instead of routing to the notice, and the SnackBar copy carries its accents in both screens. All four v1 issues are resolved and the changes introduce no regressions in the realtime wiring, the untouched existing flows, or the pure gate.

**Watch for:** nothing blocking. One minor note carried from v1 — the DELETE-propagation path is now correct by construction but still unverified by an integration test (possible); the pure gate suite is unchanged and the delete behavior depends on a live Supabase, so this remains a known, accepted coverage gap rather than a defect.

**Verdict**: APPROVED

## High-level view

The DELETE gap is closed at the right layer. Migration 0043 now runs `alter table ... replica identity full` on both `shopping_list_items` and `tasks` before the publication `DO` blocks, so a DELETE event carries the full old row including `home_id`; the client-side `home_id` filter can finally evaluate it and the deletion reaches the other member live. `ALTER TABLE ... REPLICA IDENTITY FULL` is naturally idempotent (it sets table state, not an additive object), so re-running the migration is safe, and it changes no RLS policy — cross-household isolation is unaffected.

The duplicate-channel collision is gone. Both topics now embed `identityHashCode(this)`, so the embedded and pushed `ShoppingListScreen` instances subscribe under distinct topics and each `removeChannel` in `dispose` tears down only its own channel. The same scheme was applied to tasks for consistency even though it is single-instance; harmless and defensible.

The notice asymmetry is resolved. Shopping no longer calls the throwing `_homeId()` (now fully removed, not merely bypassed); it resolves `currentUser` + `profiles.home_id` inline exactly like tasks and returns silently when either is absent. A missing session no longer surfaces the "sin conexión en vivo" notice; the notice fires only from the `catch` on a genuine channel-open failure and from `_onChannelStatus` on error/closed/timeout — the same path in both screens.

The copy fix is literal and complete: both screens now show `Sin conexión en vivo ahora mismo; se actualizará al recargar.` with correct accents.

### v1 #1 — DELETE events under the home_id filter — RESOLVED (confirmed)

Migration 0043 adds, before the two publication `DO` blocks:

```sql
alter table public.shopping_list_items replica identity full;
alter table public.tasks replica identity full;
```

This is the correct mechanism for the problem flagged in v1. By default Postgres emits only the replica identity (the PK) in a DELETE's old-row image, so a filter on `home_id` — not part of the default identity — cannot be evaluated and the event is dropped before delivery. `REPLICA IDENTITY FULL` makes the old-row image carry every column including `home_id`, so the `eq('home_id', homeId)` filter matches and `_deleteItem` (shopping) / `_delete` (tasks) now propagate live. The identity change is set before the tables are added to `supabase_realtime`, and the statement is inherently idempotent — it sets durable table state rather than adding an object, so re-running neither errors nor accumulates. It is not an RLS/policy change, so the cross-household guarantee is untouched. Deletions now meet the "instant" promise, not just the check-off and claim UPDATE flows.

### v1 #2 — duplicate channel across embedded and pushed shopping instances — RESOLVED (confirmed)

The topic is now `public:shopping_list_items:$homeId:${identityHashCode(this)}`. Because `identityHashCode` is per-object, the embedded `ShoppingListScreen` (in `DespensaTab`'s always-alive IndexedStack) and the pushed route from `home_tab` each get a distinct topic, so there is no shared-topic collision and popping the pushed route tears down only its own channel in `dispose`. The identical scheme is applied to `tasks`, which is single-instance (via `main_shell`), for consistency. One residual behavior worth naming: while the pushed shopping route is on screen, two live channels coexist, so each change triggers two independent `_reload()` calls — redundant work, not a correctness problem (`_reload()` is idempotent and DB-authoritative), and inherent to the screen being mounted twice, which the briefing permits (one channel per live screen).

### v1 #3 — inconsistent notice on auth/config failure — RESOLVED (confirmed)

Shopping's `_subscribeRealtime` no longer calls the throwing `_homeId()` helper; that helper is removed entirely (a grep for `_homeId` in the file returns nothing, so no dead code lingers). It now reads `_client.auth.currentUser` and `profiles.home_id` via `maybeSingle()` inline and `return`s on a null user or null home — byte-for-byte the pattern tasks already used. A missing session therefore produces no SnackBar. The notice is reachable only from the `catch` wrapping the channel open and from `_onChannelStatus` translating a `channelError`/`closed`/`timedOut` into the gate — i.e. genuine connectivity/channel failures — identically in both screens. The two paths are now symmetric.

### v1 #4 — SnackBar accents — RESOLVED (confirmed)

Both screens render `Sin conexión en vivo ahora mismo; se actualizará al recargar.` with the two previously-missing accents restored; the SnackBar shape (floating, `RoundedRectangleBorder` at `AppRadius.md` = 16) is unchanged.

### Regression surface — no new issues

The fixes are confined to the realtime wiring. None of the existing flows the briefing lists as untouchable appear in `9ef75b4` — `_toggleChecked`/`_addToPantry`/`_deleteItem`, the Dismissible, `ShoppingCelebrationGate`/confetti, aisle grouping and the cost card on shopping; `_complete`/`_claim`, Bolsa Común, the scoreboard/`_PointsChart` and `HomeModule.points` gating on tasks. No new dependency was added (`identityHashCode` is a `dart:core` built-in). The orchestrator's CI-exact run confirms format clean, analyze clean, 288 tests passing (≥ 281), and dependency-map up to date.

### Test coverage — unchanged, one accepted gap

`realtime_sync_test.dart` is not modified; the pure gate and `isRealtimeFailure` truth table still carry the testable logic, and the screens still translate Supabase's `RealtimeSubscribeStatus` into that pure enum. Not tested: the DELETE-propagation behavior the migration now enables, and the screen-level channel open/close wiring — both need a live Supabase or a channel fake. This is the same accepted gap noted in v1; the fix is a schema/topic change verifiable by inspection, so the risk of it silently regressing is low, but an integration test would be the only thing that proves the live DELETE path end to end.
