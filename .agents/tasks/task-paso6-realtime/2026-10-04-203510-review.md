# Supabase Realtime for shopping list and tasks (v1)

PASO 6 wires Supabase Realtime into the shopping list and tasks screens so that when one household member checks off a product or claims a task from the Bolsa Común, the other member's screen updates without a manual reload. Each screen opens exactly one `home_id`-filtered channel in `initState`, re-queries the database on any change via the existing idempotent `_reload()`, and closes the channel in `dispose`. Connection failures are surfaced once through a pure notify-once gate as a card-style floating SnackBar, never blocking the UI. The design is additive: with realtime down, both screens behave exactly as before via `FutureBuilder`/`_reload`. A new migration adds both tables to the `supabase_realtime` publication; a new pure helper (`realtime_sync.dart`) carries the testable decision logic, covered by `test/realtime_sync_test.dart`.

**Watch for:** DELETE events are filtered by `home_id` but neither table sets `REPLICA IDENTITY FULL`, so deletions likely won't reach the other user instantly (likely). `ShoppingListScreen` is instantiated both embedded in the always-alive IndexedStack and as a pushed full-screen route, so two channels with the identical topic name can coexist and tear each other down (possible). Shopping and tasks disagree on whether an auth/config failure shows the "no live connection" notice (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The core user flows both resolve to UPDATEs — checking a shopping item (`checked` update) and claiming a task (`assigned_to` + completion updates). UPDATE events carry the full new row including `home_id`, so the server-side filter matches and these changes propagate instantly. The requirement as the user stated it is met for the flows they named.

Deletions are the weak point. Postgres only ships the primary key for DELETE events unless the table has `REPLICA IDENTITY FULL`; neither `tasks` nor `shopping_list_items` sets it, and a filter on a non-identity column (`home_id`) drops events it can't evaluate. A task or shopping item deleted by one user likely stays on the other user's screen until a reload — a gap against the "instant" promise, though not one of the two flows the user called out.

Security posture is sound. Both tables have RLS keyed to `home_id = auth_home_id()`, and the realtime channel runs under the authenticated token, so a client only receives its own household's changes; the explicit `home_id` filter is defense in depth. The migration is idempotent and correctly sequenced as 0043.

Channel lifecycle is clean for tasks (single IndexedStack child, one open/one close). Shopping is more fragile: it is also pushed as a standalone route from the home tab, so a second state object opens a channel with the same topic string as the embedded one. The duplicate subscription causes redundant reloads while the route is up, and removing one channel may disturb the other since they share a topic.

The failure path never blocks the UI and fires at most once per connection drop via the pure gate, which is cleanly extracted and well tested. The one inconsistency: shopping treats a missing user/home as a live-connection failure (shows the notice), while tasks silently returns in the same situation.

<summary>Details</summary>

### DELETE propagation gap under the home_id filter

Supabase Realtime applies the row filter against the record it receives for each event. For INSERT and UPDATE that record is the full new row, so the `home_id = <homeId>` equality matches and the other user's screen reloads. For DELETE, Postgres only emits the old row's replica identity — the primary key by default — unless the table is set to `REPLICA IDENTITY FULL`. A filter on `home_id`, which isn't part of the default identity, cannot be evaluated against a DELETE payload, so those events are dropped before they reach the client.

Concretely: `_deleteItem` in shopping and `_delete` in tasks issue real `DELETE`s. The acting user sees the row vanish via their own `_reload()`, but the other household member likely won't — the row lingers until they reload manually. This is a `likely` gap (the exact drop behavior depends on the realtime server version, but the replica-identity constraint is well established). The two flows the user explicitly named (check-off and claim) are UPDATEs and are unaffected, which is why the verdict hinges on scope rather than the headline flows.

Fix options: add `alter table public.tasks replica identity full;` and the same for `shopping_list_items` to migration 0043 (RLS still prevents cross-household delivery), or remove the `home_id` filter and lean on RLS plus the idempotent reload.

### Shopping's double channel across embedded and pushed instances

`ShoppingListScreen` is mounted two ways: `const ShoppingListScreen(embedded: true)` inside `DespensaTab` (which lives in the always-alive IndexedStack) and `push(MaterialPageRoute(builder: (_) => const ShoppingListScreen()))` from `home_tab.dart`. Each `_ShoppingListScreenState` runs `_subscribeRealtime()` in `initState`, and both compute the same topic string `public:shopping_list_items:$homeId`.

```
IndexedStack (always alive)
  └── DespensaTab → ShoppingListScreen(embedded) ── channel "public:shopping_list_items:<home>"
Navigator push from HomeTab
  └── ShoppingListScreen() ───────────────────────── channel "public:shopping_list_items:<home>"  ← same topic
```

While the pushed route is on screen, two subscriptions exist for the same table and home, so every change triggers two `_reload()` calls. More concerning, the two states key their channels by an identical topic; when the pushed route is popped and its `dispose` calls `_client.removeChannel(...)`, it may disturb the subscription the embedded instance still relies on. This is `possible` — the exact outcome depends on how the client dedupes topics — but the shared-topic collision is real and avoidable by making the topic unique per state (e.g. append a UUID) or by not subscribing in the pushed instance. Tasks has only one instantiation (`main_shell.dart`) and is not affected.

### Inconsistent notice on auth/config failure

The asymmetry is in what counts as a failure. Shopping's `_subscribeRealtime` calls `_homeId()`, which throws when there's no authenticated user or no home; that throw is caught and routed to `_notifyRealtimeDown()`, showing the "sin conexión en vivo" notice. Tasks resolves the profile inline and simply `return`s on a null user or null home, showing nothing. A missing session isn't a live-connection problem, so the tasks behavior is the correct one; shopping should match it rather than mislabel an auth/config state as connectivity.

### SnackBar copy drops accents

The notice's shape (floating, `RoundedRectangleBorder` at `AppRadius.md` = 16, no red background, no jargon) meets the card-look and design-system constraints, but the copy drops two accents: "conexion" and "actualizara" should be "conexión" and "actualizará". User-facing Spanish copy for a non-technical user should carry correct accents.

### Idempotent re-query covers related tables for free

Responding to every event with a full `_fetch`/`_load` re-query (rather than patching local state from the payload) means a local write and its own realtime echo converge on the same server state, avoiding duplicate rendering without any dedup logic. It also covers tables outside the publication: the tasks scoreboard reads from `task_points`, which has no channel, yet a claim's `tasks` UPDATE triggers a `_reload()` that re-reads points — so the scoreboard stays correct on the other screen for free.

### Security: no cross-household exposure

Both tables already enable RLS with `home_id = public.auth_home_id()` select policies (0026, 0009), and because the realtime channel authenticates with the user token, a client receives only its own household's row changes — the client-side `home_id` filter is redundant defense in depth, not the sole barrier. Migration 0043 changes no policies; it only adds the two tables to the `supabase_realtime` publication, inside `DO` blocks that check `pg_publication_tables` first so re-running is safe. No cross-household exposure is introduced.

### Test coverage

`realtime_sync_test.dart` fully exercises the pure surface: `isRealtimeFailure` across all four states and the gate's notify-once / rearm-on-subscribe / manual-reset behavior, plus the clean-start case where an immediate `subscribed` leaves no pending notice. Not tested: the screen-level network wiring (channel open/close, the Supabase→pure state translation in `_onChannelStatus`, the dispose teardown) and the DELETE-propagation behavior — understandable given these need a live Supabase or a channel fake, but it means the duplicate-channel and delete-filter concerns above are not caught by the suite.
