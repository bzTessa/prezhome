# Design-system tokens and animation library, applied to Inicio (v1)

Fase 1 of a new visual language for PrezHome: a token layer (`lib/theme/`: spacing, radius, elevation, semantic Nunito text styles) plus a small framework-only animation library (`lib/widgets/animations/`: press-scale, staggered entrance, animated counter, micro-celebration), all wired into the home/Inicio tab. The approach keeps the Cozy identity and the Miau mascot, extends `AppColors`/`AppTheme` additively, and routes every animation through a single `AppMotion.reduceMotionOf` check so the whole thing collapses to a static layout under `MediaQuery.disableAnimations`. The Inicio redesign is purely presentational — all data loading, personalization, navigation, and task-completion logic is untouched. The deliberately-skipped `main_shell` tab transition is correctly out of this diff.

Watch for: AnimatedCounter is built with `Tween(begin: value, end: value)`, so it never animates on first mount and the only motion it shows is on *subsequent* value changes (confirmed). `AppMotion.lerpDouble` is covered by seven tests but is not called by any production widget — it is a test-only function (confirmed). Neither is a regression; both are minor polish/clarity issues.

**Verdict**: APPROVED

## High-level view

The token layer is additive and non-breaking: no existing `AppColors` constant or `AppTheme.cardDecoration` was removed, the new `surfaceDecoration` sits alongside the old one, and `app_theme.dart` re-exports the token files so a single import pulls the whole scale. No backend, migration, or `supabase/` file is in the diff, and `pubspec.yaml` is unchanged — the large `pubspec.lock` churn is a lockfile re-resolution of dependencies already declared on `main`, not new packages.

Accessibility is handled consistently. Every one of the four animation widgets consults `AppMotion.reduceMotionOf(context)` and renders its final state (or zero-duration) when reduce-motion is on; `Celebrate` additionally refuses to mount its overlay at all. This is the right fail-safe direction — motion off means static layout with no loss of content.

The Inicio redesign is a presentation-only rewrite. The diff touches widget tree, styles, colors, and animation wrappers, but not a single Supabase query, `setState` payload, `TaskScheduler.complete` call, `Navigator` push, or `DashboardPrefs` read/write. The task-completion SnackBar string and `refreshActiveView` are intact, so the behavioral contract of the screen is preserved.

Two small correctness/clarity items stand out: AnimatedCounter does not animate on first render by construction, and the pure `lerpDouble` helper that 7 tests exercise is not actually what AnimatedCounter uses, so those tests validate a function no screen depends on.

1. **AnimatedCounter never animates on first mount** — `Tween(begin: value, end: value)` means the intro render jumps straight to the value; only later value changes animate. If an intro count-up was intended, seed `begin` from a previous/zero value. Otherwise document that it animates on change only.
2. **lerpDouble is test-only** — the pure helper has 7 tests but no production caller (AnimatedCounter uses `TweenAnimationBuilder`). Either wire it into AnimatedCounter so the tests guard real behavior, or drop it and its tests to avoid a false sense of coverage.

Acceptable for a dashboard that settles quickly, but worth a key or a "run once" guard if flicker appears.

### Reduce-motion is honored uniformly, and fail-safe

All four widgets gate on `AppMotion.reduceMotionOf`, and the gating direction is fail-safe — motion off yields the final, fully-legible state, never a half-finished one. The behaviors worth confirming individually: `PressScale` keeps `scale == 1.0` but still fires `onTap`, so pressable targets stay functional without the shrink; `StaggeredEntrance` returns its `child` directly at final position and full opacity; `AnimatedCounter` resolves to `Duration.zero` and shows the number immediately; `Celebrate.show` returns before inserting any `OverlayEntry`, so the mascot pop never mounts. The single-source helper (with a `maybeOf` null-fallback to `false`) keeps accessibility reasoning in one place.

### AnimatedCounter: begin == end skips the first-render animation

```dart
return TweenAnimationBuilder<double>(
  tween: Tween<double>(begin: value, end: value),
  ...
);
```

`TweenAnimationBuilder` animates from the *previous* tween's `end` to the new `end` whenever the tween changes, and uses `begin` only for the very first build. With `begin == end == value`, the first build has nothing to traverse, so the counter appears at its final value with no count-up. Subsequent value changes still animate correctly (old end → new end), which is the common case on a dashboard that reloads. (confirmed, by reading the widget and Flutter's `TweenAnimationBuilder` contract.)

The inline comment ("Dejamos `begin` por si es el primer render (así parte del valor final)") describes the effect as intentional while the surrounding doc comment advertises animating "de su valor anterior al nuevo", which reads as if a first-render intro were expected. If an initial count-up from zero was wanted, seed `begin` with `0` (or a prior value); if not, the doc comment should say "animates on value change only."

### lerpDouble is validated in isolation but unused in production

`AppMotion.lerpDouble` is a clean pure function with thorough tests (midpoints, clamping, euro/kcal formatting). But AnimatedCounter — the only numeric animation in the app — uses `TweenAnimationBuilder` with Flutter's own interpolation, not `lerpDouble`. (confirmed: `grep` across `lib/` finds no production caller.) The seven `lerpDouble` tests therefore guard a helper nothing depends on. The `effectiveDuration` and `staggerDelay` tests, by contrast, cover functions the widgets genuinely call, so reverting that logic would break real behavior and fail the suite. Recommend either routing AnimatedCounter through `lerpDouble` so its tests become meaningful, or removing the function and its tests.

### StaggeredEntrance simulates delay inside one tween — scroll-safe, rebuild-sensitive

Rather than a per-item `Timer` or an `AnimationController`, the stagger inflates the tween duration by the item's delay and clips the opening fraction, so each item sits at opacity 0 until its turn. This keeps everything inside a single `TweenAnimationBuilder` that runs once per build and never loops, which is the right call for scroll performance — there is no timer to leak and no rebuild storm. The `maxItems` cap (default 8) stops long lists from accumulating runaway delays. The one caveat is that, being stateless and un-keyed beyond list position, a `setState` from `_loadDashboard` landing mid-entrance will rebuild the subtree and restart the fade/slide from zero. On the Inicio dashboard the reloads settle fast and the cards are few, so this is unlikely to be visible; flag it only if entrance flicker shows up when data arrives late.

### Celebrate overlay lifecycle has no leak or input-blocking gap

The one place a fire-and-forget overlay usually leaks or steals input is covered here: the burst removes its own `OverlayEntry` on completion and disposes the controller, and `IgnorePointer` wraps it so it never captures touches from the screen underneath. It layers on top of the existing points SnackBar rather than replacing it, so the established feedback is preserved.

### Inicio redesign preserves the behavioral contract

The home-tab change is presentation-only. The data-loading methods (`_loadPrefs`/`_savePrefs`, `_loadTodayPlan`, `_loadTasksSummary`, `_loadEconomySummary`, `_loadCaloriesSummary`, `_loadExpirySummary`, `_loadReminders`), their per-section try/catch isolation, the `TaskScheduler(_client).complete(task)` path, the `'¡+${task.points} puntos!'` SnackBar, `refreshActiveView`/`_loadDashboard`, quick-action navigation with refresh-on-return, and the `DashboardPrefs` ordering/visibility all survive unchanged — the diff over those lines is empty except for one added comment. Task completion now also fires `Celebrate.show(context)` before the SnackBar, which is purely additive and reduce-motion-safe. Color-by-card and the pastel accent pairs reuse existing `AppColors` chip tones, keeping the Cozy palette coherent.

### Token layer and dependency surface

`AppColors` gains `inkMuted`/`faintShadow`/`mediumShadow` and `AppTheme` gains `surfaceDecoration({radius, elevation, color})` with a 0/1/2 elevation switch mapping to `AppElevation` levels; `cardDecoration` and every pre-existing color constant remain, so nothing downstream breaks. `app_theme.dart` re-exports the four token files, and the token files do not import back into `AppTheme`, so there is no import cycle. No `pubspec.yaml` change and no `supabase/`, migration, or `.sql` file in the diff. The sizeable `pubspec.lock` delta (fl_chart, image_picker, file_selector, cross_file, equatable) is lockfile re-resolution: those packages are already declared in `main`'s `pubspec.yaml`, and `main`'s committed lock was stale (it did not list them), so `flutter pub get` regenerated it here. The generated plugin registrants for linux/macos/windows are a byproduct of the same resolution. Worth noting so the lock churn isn't mistaken for a dependency change, but not a concern.

### Test coverage

The 18 new tests are pure-logic and meaningful for `effectiveDuration` (reduce-motion → zero, identity otherwise) and `staggerDelay` (monotonic growth, `maxItems` cap, zero for index ≤ 0 and under reduce-motion) — reverting that logic would fail them. Not tested: the widgets themselves. There is no widget test asserting that PressScale still fires `onTap` under reduce-motion, that StaggeredEntrance/AnimatedCounter render their final state when `disableAnimations` is true, or that Celebrate skips the overlay — these behaviors are the actual accessibility guarantee and currently rest on code inspection. A few `pumpWidget` tests with `MediaQuery(disableAnimations: true)` would lock them in.
