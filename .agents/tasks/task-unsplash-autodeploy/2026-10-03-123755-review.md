# Unsplash as primary recipe-photo provider, with CI auto-deploy of all edge functions (v1)

`recipe-photo` now prefers Unsplash over Pexels: when `UNSPLASH_ACCESS_KEY` is present it hits `search/photos` with `Client-ID` auth, best-effort fires Unsplash's required `download_location` trigger, and returns a richer `{url, provider, attribution}` payload; Pexels stays as an untouched fallback and the whole function still degrades to `{url:null}` / 200 on any missing key, provider failure, or empty result. The CI side adds a `deploy-functions` job that triggers on `supabase/functions/**`, deploys all five functions by name after migrations, and keeps JWT verification on. Docs are rewritten in Spanish so Tessa's only action is pasting `UNSPLASH_ACCESS_KEY` into the Supabase web panel, no terminal. The Flutter callers read only `data['url']`, so the enriched response is backward-compatible with no `lib/` changes.

Watch for: the Unsplash `download_location` call is `await`ed inside the request path, so a slow trigger endpoint adds latency to every photo lookup even though it can't fail it (confirmed). Attribution is returned but never surfaced in the UI, which is a soft spot against Unsplash's attribution terms (confirmed, flagged by the author as future work). No automated coverage of the new provider path exists (confirmed, acknowledged — no Deno runner in-repo).

**Verdict**: APPROVED

## High-level view

The provider selection is a clean primary/fallback split keyed purely on which secret exists: `UNSPLASH_ACCESS_KEY` short-circuits to Unsplash, otherwise the old Pexels path runs verbatim. Unsplash's search and the mandatory download trigger are each wrapped so no failure escapes to the request handler, preserving the never-500 contract. The one behavioral cost is that the download trigger is awaited rather than fire-and-forget, so it sits on the critical path.

The response shape grows (`provider`, `attribution`) but the two Flutter callers only read `url`, so nothing downstream breaks and no migration is needed. Attribution data is collected but not displayed anywhere, which is the open compliance gap.

CI now deploys edge functions automatically on changes under `supabase/functions/**`, as a second job gated on the migrations job so function code never lands ahead of its schema. Functions are deployed by explicit name with JWT verification left on, and the job scopes itself to `SUPABASE_ACCESS_TOKEN` only — no DB password, no env dumps, no secret echoes. Docs match the automation: the only manual step left for the user is adding one secret in the Supabase panel.

### Provider selection and the never-500 contract

Selection is a precedence check at the top of step 4: if `unsplashKey` is set, return `searchUnsplash(...)` and never touch Pexels; Pexels only runs when the Unsplash key is absent. In the deployed configuration (Unsplash key present) the Pexels block is dormant, which is the intended fallback shape and leaves the Pexels code byte-for-byte unchanged.

Every Unsplash failure mode resolves to `{url:null}` / 200: a top-level try/catch absorbs any network throw or JSON error, a non-OK response logs and degrades, empty `results` degrades, and a missing `urls.regular`/`urls.small` degrades. The only paths that still return non-200 are the pre-existing auth/profile/validation checks (401/400/500 for incomplete server config), none of which this change touched.

### Awaited download trigger adds latency

The download trigger is isolated in its own try/catch so a failure can't break the response. The subtlety is that it's `await`ed:

```ts
if (typeof downloadLocation === "string" && downloadLocation.length > 0) {
  try {
    await fetch(downloadLocation, { headers: { Authorization: `Client-ID ${key}` } });
  } catch (e) {
    console.error("Unsplash download trigger exception:", e);
  }
}
```

The response to the Flutter client is held until this second round-trip to Unsplash completes. On a slow or stalled trigger endpoint, the user's recipe-save photo lookup waits for it with no timeout bound. The trigger's result is discarded, so this is a candidate for fire-and-forget (drop the `await`) or an `AbortController` timeout, so download-trigger latency can't degrade the user-facing call.

### Response shape and client compatibility

Unsplash returns `{url, provider:"unsplash", attribution:{photographer, photographerUrl, source, sourceUrl}}`; Pexels still returns bare `{url}`. The two callers (`add_recipe_screen.dart`, `discover_recipes_screen.dart`) both do `data['url']?.toString()` and ignore the rest, so the asymmetry between the two providers' payloads is harmless and no migration or model change is required. The attribution block is populated from `user.name` and `user.links.html` with null-safe fallbacks, but nothing in `lib/` reads it — so Unsplash's expectation that photographer credit be displayed is not yet met. The author documented this as intentional future work in the function header; worth tracking rather than blocking.

### CI deploy job: ordering, scope, and secret hygiene

The new `deploy-functions` job `needs: deploy`, so functions deploy only after migrations succeed and inherit the `production` environment gate — new function code can't run against an un-migrated schema. It deploys the five functions by explicit name, matching exactly what's on disk under `supabase/functions/` (analyze-meal, discover-recipes, generate-recipe, recipe-photo, scan-ticket), and deliberately omits `--no-verify-jwt` so each function keeps validating its own JWT.

On secret hygiene the job is tight: its `env:` exposes only `SUPABASE_ACCESS_TOKEN`, deliberately dropping `SUPABASE_DB_PASSWORD` since it doesn't touch the DB, and `SUPABASE_PROJECT_REF` is interpolated inline into `supabase link`/`deploy`. No `env`/`printenv`/`set -x`, no secret echoed. The `paths` trigger now includes `supabase/functions/**` alongside migrations, so function-only changes actually deploy. One deploy-by-name trade-off worth noting for later: adding a sixth function means editing this workflow, since the explicit list won't pick it up automatically — a conscious choice the author documents in the job comment.

### Docs

The docs drop the terminal `supabase secrets set` / `functions deploy` steps and separate GitHub Actions repository secrets (CLI/migrations) from Supabase Edge Function secrets (`UNSPLASH_ACCESS_KEY`, `GEMINI_API_KEY`) — the exact confusion a non-technical user would hit. Spanish throughout, no em dashes in the changed files.
