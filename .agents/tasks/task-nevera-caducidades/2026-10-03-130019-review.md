# Expiry tracking for fridge, freezer and pantry (pass v1)

Adds a single expiry model to `InventoryItem` (effective expiry date, days-until, a four-value `ExpiryStatus`, and Spanish labels), redesigns the inventory screen to group food by location with soonest-first sorting and a per-item status chip, surfaces an optional "Caduca el" date picker in the add screen, and adds a "Caducidades" dashboard card on the home tab that counts food expiring soon / already expired. The design choice is one semantics rule the user never has to think about: Nevera/Despensa read `expiration_date` (falling back to `best_before`), Congelador reads `best_before` (falling back to `frozen_on + 90d`). Thresholds are warm and simple: `<0` caducado, `<=3` pronto, else fresco, no date => sinFecha. No DB migration is added (columns already exist; migrations still end at 0032), FAB heroTag stays `fab-inventory`, and the cozy Spanish tone with Miau is preserved.

Watch for: the dashboard count and the inventory view use the same `expiryStatus` source so they stay consistent (confirmed); the chip's far-future date string `Caduca D/M` drops the year and leading zeros, which can read ambiguously across a year boundary (confirmed, cosmetic); unbraced `if` statements in the section-header summary slipped past the formatter but are a lint-style outlier versus the rest of the file (confirmed, cosmetic).

**Verdict**: APPROVED

## High-level view

The expiry logic lives entirely in `InventoryItem` as pure getters, which is what makes it testable and keeps the two consumers (inventory screen, home dashboard) honest: both derive their counts from the same `expiryStatus`, so the "3 caducan pronto" on the dashboard cannot silently disagree with the chips in the list. The location-specific rule (freezer uses best-before or a 90-day default window; everywhere else uses the explicit expiry date) is collapsed into `effectiveExpiry`, so callers never branch on category themselves.

The inventory screen moved from a flat list to location sections (Nevera, Congelador, Despensa, then non-food "Hogar y limpieza"), each sorted soonest-expiry-first with undated items pinned last, and each food header carrying a short caducado/pronto summary. All previously hardcoded hex colors were swapped for `AppColors`/`AppTheme`, and the existing behaviors (type filter, staple toggle, delete, badges, Miau empty state, FAB heroTag) are carried over intact.

The dashboard card reads the home's food inventory, counts pronto/caducado with the same enum, and degrades to a reassuring "Todo fresco" state on empty or on error — errors are logged rather than surfaced, so a failed load looks identical to an empty fridge. That is a deliberate, defensible trade-off for a non-technical user, noted below.

Tests are pure-logic unit tests over the new getters with time-relative dates, covering both location rules, the fallback chain, and all four status buckets. The UI grouping/sorting and the dashboard counting are not covered, which is the main gap.

<summary>Details</summary>

### One expiry rule across three locations

`daysUntilExpiry` normalizes "today" to midnight before differencing, and because `expiration_date`, `best_before` and `frozen_on` are all parsed from date-only strings in `fromMap`, there is no time-of-day drift that could push a boundary day off by one — the one subtle correctness point worth confirming in this logic.

The add screen writes `expiration_date` only for non-Congelador food and `frozen_on` only for Congelador food, so the two inputs never collide and `effectiveExpiry`'s branch always has at most one authoritative source per location. A Congelador item created without a `frozen_on` resolves to `sinFecha` rather than inventing a window from an unknown freeze date.

### Grouping and soonest-first sort

`_groupIntoSections` partitions by `itemType` first (non-food into "Hogar y limpieza"), then food by `category`, with any unexpected category folded into Despensa so nothing is dropped. The sort comparator pushes null-day items to the end and otherwise orders by ascending days-until-expiry, surfacing the most urgent items at the top of each location.

The per-section header summary counts pronto and caducado within that section only, while the dashboard counts across all food locations — different scopes by design (per-location detail vs. whole-home alert), both derived from `expiryStatus`, so they cannot drift apart.

### Status chip wording

`_label()` produces day-aware Spanish (`Caducado`, `Caduca hoy`, `Caduca mañana`, `Caduca en N días` for the pronto band) and a bare `Caduca D/M` date for fresco/distant items. That last branch drops the year and zero-padding, so an item expiring 3 January shown in December reads as `Caduca 3/1` with no way to tell it is next year. The add screen already formats dates as `dd/mm/yyyy`; aligning the chip would remove the ambiguity.

### Dashboard card fails to a calm empty state

On any error, `_loadExpirySummary` logs with `debugPrint` and leaves the counts at zero, so the card shows "Todo fresco por aquí 🐾" — a load failure is indistinguishable from an empty, all-fresh fridge. For this audience (non-technical, cozy UX) failing closed to a reassuring message rather than an error banner is a defensible trade-off, and the counts refresh when the user returns from the pushed `InventoryScreen`, so a transient failure self-corrects on the next open. Flagged so the choice is explicit, not as a blocker.

### Test coverage

`inventory_expiry_test.dart` uses dates relative to `now` (so the suite won't rot) and covers the Nevera/Despensa path (expired, today=0, tomorrow=1, boundary=3, far=fresco, no-date, best_before fallback, expiration-over-best_before precedence) and the Congelador path (best_before used, frozen_on+90 fallback, both-null => sinFecha, window-exhausted => caducado), plus the retained `daysUntilBestBefore`. Thorough for the model.

Not tested: the section grouping and the soonest-first comparator (including the null-last tie-break), and the dashboard counting in `_loadExpirySummary`. Both are plain logic and would be cheap to cover if the sort comparator were lifted out of the widget.
