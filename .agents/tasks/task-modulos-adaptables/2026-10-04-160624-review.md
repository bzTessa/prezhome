# Propagación del cambio de módulos a las tres entradas del wizard (v2)

Segunda pasada sobre `feat/paso2-modulos-adaptables`. La v1 devolvió NEEDS_CHANGES por un único bloqueante: al cambiar módulos en el wizard, solo la entrada de primer arranque (`home_session_screen` → `refreshHome()`) refrescaba la barra inferior; las otras dos (aviso de calorías en Inicio y perfil nutricional) dejaban las pestañas obsoletas hasta reiniciar. El commit de seguimiento (`9d7189c`) introduce una clave estática compartida `MainShell.shellKey` y un helper estático `MainShell.reloadModules()`, y conecta a él las dos salidas que faltaban. El arreglo es correcto para el flujo normal post-login y no toca nada de lo que v1 ya aprobó; sigue en 219 tests verdes y `analyze` limpio.

**Watch for:** el helper estático solo alcanza al shell cuando este se construyó con `MainShell.shellKey`. El shell del flujo de alta de hogar (`home_onboarding_screen` → `const MainShell()`, sin clave) **no** lleva esa clave, así que si un usuario recién llegado abre el wizard desde el aviso de calorías dentro de ese shell y apaga un módulo, `reloadModules()` resuelve `currentState == null` y no refresca la barra (*confirmed* que ese shell no usa la clave; *likely* que la ruta sea alcanzable con perfil incompleto). No es una regresión —antes no existía propagación cruzada alguna— pero deja la afirmación "las tres entradas avisan al shell" incompleta para ese arranque.

**Verdict**: APPROVED

## High-level view

La propagación se apoya en una clave global estática (`MainShell.shellKey`) en lugar de un lookup por ancestro, forzado porque las rutas que empuja el `Navigator` raíz (el wizard abierto desde la pantalla de perfil) son hermanas del shell, no descendientes, de modo que `findAncestorStateOfType` nunca lo habría encontrado. `home_session_screen` construye el shell con esa misma clave y las dos salidas antes huérfanas (`home_tab._calorieGoalPrompt`, `nutrition_profile_screen`) llaman `MainShell.reloadModules()` al volver. Para el flujo post-login el bloqueante de v1 queda resuelto.

El patrón de clave estática es seguro en este producto: hay un único shell vivo a la vez (cada transición usa `pushReplacement`/`pushAndRemoveUntil`, nunca dos shells apilados), así que no hay riesgo de clave global duplicada, y el helper es no-op cuando el shell no está montado —lo que mantiene los tests que no montan shell sin tocar. La única grieta es que el shell del alta de hogar se sigue construyendo sin la clave compartida, por lo que ese arranque concreto no recibe el aviso.

El resto de lo que v1 aprobó sigue intacto: el commit de seguimiento no toca `dashboard_prefs.dart`, `profile_wizard_screen.dart`, `tasks_screen.dart` ni `household_screen.dart`; solo añade imports de `main_shell` en las dos pantallas y la clave/helper en el shell. La tolerancia ausente-vs-vacío, el no-clobber de cards/hidden/quick, los índices por identidad y el gating de Modo Puntos no cambian.

<summary>Details</summary>

### La clave compartida alcanza al shell vivo del flujo post-login

`MainShell.shellKey` es una única instancia estática; `home_session_screen` la toma literalmente (`final GlobalKey<MainShellState> _shellKey = MainShell.shellKey;`) y construye `MainShell(key: _shellKey)`. La única otra construcción de `MainShell` —la de onboarding— no pasa clave distinta (ver más abajo), así que para este flujo `shellKey.currentState` apunta al `State` montado.

```
wizard (home_tab / nutrition_profile)  ── pop ──▶ MainShell.reloadModules()
                                                        │  (static)
                                                        ▼
                                   shellKey.currentState?.reloadModules()
                                                        │  (instancia)
                                                        ▼
                                              _loadPrefs() ─▶ setState + _rebuildTabs()
```

`_rebuildTabs()` recomputa pestañas y reclampa `_index` a Inicio si la activa desaparece, de modo que apagar Tareas desde cualquiera de las dos entradas ahora sí quita la pestaña sin dejar `_index` fuera de rango. La ruta de primer arranque conserva `refreshHome()`, que además refresca la vista de Inicio para el objetivo de calorías recién calculado.

### El shell de alta de hogar se construye sin la clave

`home_onboarding_screen._runHomeAction` hace `Navigator.pushAndRemoveUntil(... const MainShell())`: ese shell no recibe `MainShell.shellKey`. Tras crear o unirse a un hogar, el usuario queda dentro de ese shell con el perfil típicamente incompleto, condición que muestra el aviso de calorías en Inicio. Si desde ahí abre el wizard y apaga un módulo, al volver `MainShell.reloadModules()` evalúa `shellKey.currentState`, que es `null` para ese shell, y no hace nada: la pestaña sigue visible hasta que la app rearranque y reentre por `HomeSessionScreen` (que sí construye con la clave).

No es una regresión —la v1 no cubría este arranque y antes no había propagación cruzada— y la línea `const MainShell()` es preexistente y queda fuera del diff, por lo que no bloquea. Pero conviene registrarlo: la forma mínima de cerrarlo es construir también ese shell con `MainShell.shellKey`, igual que hace `home_session_screen`.

### Seguridad del patrón de clave estática global

Una `GlobalKey` estática reutilizada por dos `MainShell` montados a la vez lanzaría un error de clave duplicada, así que vale la pena confirmar que eso no puede pasar: las transiciones hacia el shell usan `pushReplacement` (`login_screen`) o `pushAndRemoveUntil` (`home_onboarding_screen`), y `home_session_screen` lo devuelve como única hoja del `FutureBuilder`. Nunca hay dos shells coexistiendo, de modo que la clave gobierna como mucho una instancia viva. El helper, al ser `shellKey.currentState?.reloadModules()`, degrada a no-op cuando no hay shell montado, por lo que ni los tests que montan pantallas sueltas ni las llamadas durante transición rompen.

El punto a vigilar en pruebas futuras es que un `GlobalKey` estático es estado global entre tests dentro del mismo proceso: dos widget tests que monten `MainShell` con esta clave sin desmontar el anterior chocarían. Hoy no hay ninguno (los tests de shell ejercen la función pura `computeVisibleTabIds`, no montan el widget), así que no hay fallo actual; es una restricción a recordar si se añade un widget test del shell.
