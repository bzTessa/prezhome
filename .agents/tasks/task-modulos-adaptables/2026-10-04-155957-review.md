# Módulos activables y estilo de cocina en el wizard (v1)

Añade dos conceptos al perfil del hogar: módulos encendibles/apagables (Modo Puntos, Tareas, Batch Cooking) y un estilo de cocina (Batch / Diario / Mixto). Ambos viven dentro del JSON existente `profiles.dashboard_prefs`, sin migración SQL ni tabla nueva, apoyándose en la RLS por usuario que ya protege `profiles`. El wizard gana dos páginas visuales (tarjetas seleccionables para el estilo, interruptores para los módulos) y, al guardar, fusiona solo esos dos campos sobre las prefs cargadas para no pisar la personalización de Inicio. `main_shell` deja de usar índices fijos: construye pestañas, destinos e índices desde una única lista calculada por identidad semántica, de modo que ocultar Tareas no descoloca la navegación. Tareas, Modo Puntos (marcador/gráfica + acceso a Economía) quedan condicionados al flag correspondiente.

**Watch for:** dos de las tres entradas al wizard (el aviso de calorías en Inicio y la pantalla de perfil nutricional) no refrescan el shell al volver, así que un cambio de módulos hecho desde ahí no actualiza la barra de navegación hasta un reinicio o recarga posterior (*likely*). El resto —compatibilidad hacia atrás, no-clobber de cards/hidden/quick, robustez de índices— está bien cubierto y probado.

**Verdict**: NEEDS_CHANGES

## High-level view

El modelo trata la **ausencia** de la clave `modules` como "todos activados" y una lista vacía explícita como "ninguno activado", que es la distinción correcta para que los usuarios existentes (cuyo JSON no tiene la clave) no se queden sin pestañas. `toJson` siempre emite ambas claves nuevas, lo que convierte prefs antiguas en explícitas en el primer guardado sin cambiar el comportamiento observable.

El guardado del wizard parte de las prefs ya persistidas y usa `copyWith` para tocar únicamente `enabledModules` y `cookingStyle`; `cards`/`hidden`/`quick` y el resto de columnas de `profiles` quedan intactos. El editor de dashboard de Inicio recibió el arreglo correlativo: ahora reconstruye con `widget.initial.copyWith(...)` en vez de un `DashboardPrefs(...)` nuevo, evitando que borre módulos/estilo.

`main_shell` sustituye los índices hardcodeados (`_homeIndex`, `_despensaIndex`) por `computeVisibleTabIds` + resolución por `TabId`. Páginas y destinos del `NavigationBar` salen de la misma lista, así que no pueden desalinearse; `_index` se reclampa cuando una pestaña desaparece y la navegación "Caducidades → Despensa" se resuelve por identidad. Batch Cooking persiste su flag pero aún no gobierna ninguna pieza visible (previsto para Paso 5).

El punto débil es la **propagación** del cambio de módulos: solo el lanzamiento del wizard desde `home_session_screen` llama a `refreshHome()`. Las otras dos entradas no notifican al shell, de modo que la barra inferior puede quedar desincronizada con las prefs recién guardadas hasta la siguiente recarga.

### Ausente vs. vacío en `fromJson` (compatibilidad hacia atrás)

El núcleo de la compatibilidad es distinguir dos estados que un parseo ingenuo colapsaría:

```dart
final rawModules = json['modules'];
if (!json.containsKey('modules') || rawModules == null) {
  enabledModules = DashboardPrefs.defaults().enabledModules; // todos
} else {
  // itera rawModules; ids desconocidos ignorados -> puede quedar vacío
}
```

Un usuario que ya tenía `dashboard_prefs` guardado desde Paso 1 no tiene la clave `modules`, así que entra por la rama "todos activados" y conserva las cinco pestañas. Un usuario que apaga todo en el wizard guarda `'modules': []`, que entra por la otra rama y queda con el set vacío. La prueba `fromJson sin clave "modules" ... activa todos` y `fromJson con "modules": [] respeta ninguno` fijan ambos caminos y fallarían si se perdiera el `containsKey`. Los ids desconocidos se descartan silenciosamente, lo que protege contra datos corruptos o de versiones futuras sin romper el parseo.

`cooking_style` sigue la misma filosofía fail-safe: `null`, ausente o id no reconocido caen a `CookingStyle.daily`.

### No-clobber en el guardado del wizard y en el editor de Inicio

El riesgo real de este cambio era que el wizard, al escribir `dashboard_prefs`, sobrescribiera la personalización de tarjetas que la usuaria hubiera hecho en Inicio. El guardado lo evita cargando primero las prefs (`_loadExisting` lee `dashboard_prefs`) y fusionando con `copyWith`:

```dart
final mergedPrefs = _dashboardPrefs.copyWith(
  enabledModules: {..._enabledModules},
  cookingStyle: _cookingStyle,
);
```

`cards`/`hidden`/`quick` viajan sin tocar porque `copyWith` solo reemplaza lo que recibe. La prueba `merge estilo wizard: copyWith(...) no pisa cards/hidden/quick` lo verifica contra un JSON con personalización previa y comprueba también que el update sigue siendo parcial (no pisa otras columnas de `profiles`).

El arreglo correlativo en `home_tab.dart` cierra el agujero inverso: el editor de dashboard de Inicio antes construía `DashboardPrefs(order, hidden, quick)` desde cero —lo que habría reseteado `enabledModules`/`cookingStyle` a los defaults al guardar— y ahora hace `widget.initial.copyWith(order, hidden, quick)`. Sin este cambio, reordenar tarjetas en Inicio habría reactivado módulos apagados.

### Índices por identidad en `main_shell`

La topología de navegación pasa de posiciones fijas a una lista derivada:

```
computeVisibleTabIds(prefs) -> [Comidas, Despensa, Inicio, (Tareas?), Hogar]
        │
        ├── pages        = [t.page for t in tabs]        ─┐ misma lista,
        └── destinations = [t.destination for t in tabs]  ┘ no se desalinean
```

Como `IndexedStack.children` y `NavigationBar.destinations` se generan de la misma lista, nunca difieren en orden ni longitud. El arranque en Inicio usa `_indexOf(TabId.inicio)` en vez de la constante `2`, y `_goToDespensa` resuelve `_indexOf(TabId.despensa)`, así que "Caducidades → Despensa" sigue aterrizando bien aunque Tareas desaparezca y corra los índices. `_rebuildTabs` reclampa `_index` a Inicio si la pestaña activa se evapora, y `goToTab` valida rango — dos defensas contra el `RangeError` que motivó el refactor. Las pruebas de `computeVisibleTabIds` cubren el set por defecto, Tareas apagado y el set vacío, confirmando que Tareas es la única pestaña condicional y que Inicio/Despensa siguen presentes.

### Propagación del cambio de módulos (gap)

El shell solo recarga sus prefs cuando se le avisa. `refreshHome()` —que llama a `_loadPrefs()` y por tanto reconstruye la barra— se invoca desde `home_session_screen._maybeLaunchWizard` al cerrarse el wizard de primer arranque. Pero el wizard tiene otras dos entradas:

- `home_tab.dart` (`_calorieGoalPrompt`): al volver solo hace `_loadCaloriesSummary()`.
- `nutrition_profile_screen.dart`: al volver solo hace `_load()`.

Ninguna toca el shell. `HomeTab.refreshActiveView` tampoco relee las prefs del shell (actúa dentro de la pestaña, no sobre `MainShellState._prefs`). Resultado: si la usuaria entra al wizard desde "Mi perfil nutricional" o desde el aviso de calorías y apaga, por ejemplo, Tareas, el flag se persiste pero la pestaña Tareas sigue visible hasta que el shell vuelva a cargar prefs (reinicio de la app o una ruta que reconstruya `MainShell`). `reloadModules()` existe precisamente para esto pero no se llama desde esas rutas. Conviene conectar esas dos salidas del wizard a `reloadModules()` (vía el `_shellKey` o el callback `onFinished`).

### Gating de Modo Puntos en Tareas y Hogar

El flag `points` oculta el `_Scoreboard` + `_PointsChart` en Tareas y el tile de Economía en Hogar; el resto de cada pantalla no se toca. Ambos `_...Data` default-ean `pointsEnabled = true`, de modo que un fallo de carga de prefs degrada hacia "visible" (fail-open) en lugar de ocultar funciones sin querer —coherente con el default "todos activados" del modelo.
